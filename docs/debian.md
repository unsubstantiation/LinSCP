# LinSCP on Debian

**The native desktop application is experimental and not ready for production transfers.** SFTP and plain HTTP WebDAV transfers, plus FTP and explicit/implicit FTPS staged uploads, FTP/explicit FTPS downloads and S3 small-file transfers, have live integration tests. SFTP and WebDAV directory copies between the local pane and a remote session support explicitly approved merges, but conflicting files fail without replacement; merges are not transactional and concurrent directory path changes can affect them. WebDAV directory copies require acknowledgement that trees are not snapshots and path changes may redirect writes. Other directory merges are unsupported. WebDAV and S3 file downloads support verified `.filepart` resumption with a strong ETag; the whole prefix is retransferred for verification. This relies on server-enforced conditional requests, and unchanged ETags do not necessarily identify a unique version. Existing partials are not modified or removed, and a network failure may save a new partial for retry. Other resumption modes are unsupported. WebDAV files can be moved to a new local destination using conditional GET and DELETE with the original strong ETag, relying on server enforcement; if deletion cannot be confirmed, a duplicate may remain. WebDAV files and directories can be renamed or queued for a move between directories in the same session using a strong source ETag and no-replace MOVE, relying on server enforcement. Directory ETags may not cover all descendants; concurrent subtree changes may move too and require explicit acknowledgement. Queued MOVE requests can be cancelled before they start, not during the request, and a lost or ambiguous response means the item may have moved. WebDAV files can also be moved to a connected WebDAV, SFTP or S3 session with confirmation, using an ETag-pinned download, exclusive upload and conditional source deletion. These cross-server moves are not transactional and may leave duplicate or partial destinations; S3 destinations are limited to 1 GiB. WebDAV and S3 files can be copied via a conditional temporary local download and exclusive upload to a new destination in the same session or in a connected WebDAV, SFTP or S3 session; interruption can leave a partial remote destination. S3 source ETags rely on provider enforcement and may not uniquely identify a version. SFTP files can be copied to WebDAV, SFTP or S3, and SFTP or WebDAV directories can be copied to a new SFTP or WebDAV directory, via a local stage and explicit risk confirmation. WebDAV files are individually ETag-pinned but the tree is not a snapshot. SFTP cannot pin a source snapshot; concurrent source or destination path changes can affect the result. Directory copies do not merge and can leave partial remote trees on interruption. Cross-server directory moves, S3-source moves, and other source protocols remain unsupported. Local moves require a new destination on the same filesystem. Local copies, SFTP and WebDAV transfers, FTP/FTPS transfers, and S3 transfers support cooperative cancellation. An interrupted FTP/FTPS transfer invalidates the control connection and requires reconnecting. Fresh queued file downloads use owned temporary files that are removed on cancellation or failure on a best-effort basis; cleanup can fail. Local staging and cleanup assume a trusted destination directory; concurrent pathname replacement can affect temporary files. SFTP and WebDAV directory downloads, including merges, are staged as a tree before publication; their cleanup is best-effort. New trees are published without replacement on Linux and Windows; merges are not transactional and can leave published files if interrupted. Remote uploads and merges can leave partial files or directories. Standard SFTP and FTP cannot condition deletion on the identity of the uploaded file, so the app does not automatically delete interrupted uploads by pathname and rejects legacy unguarded SFTP/FTP upload routes. Safe automatic cleanup requires server-side ownership or conditional-delete support. For new WebDAV uploads, a server that supports conditional lock-null resources allows a random locked stage, with failure cleanup conditional on the still-valid lock token. If cleanup is unconfirmed, the app retains the token in memory and retries in the background and on later staged uploads in the same session; tokens are not persisted across restarts. This relies on server lock and precondition enforcement; locks can expire, and cleanup or lock acquisition can be unconfirmed and leave a temporary resource. Servers without this capability fall back to direct exclusive or conditional PUT. Approved overwrites on lock-capable servers use tagged source-lock and destination-ETag conditions on MOVE, relying on the server to enforce both. No-overwrite uploads require an exclusive-create capability (currently SFTP, WebDAV and S3; S3 is limited to 1 GiB); Queued WebDAV and S3 file overwrites require a strong ETag and use conditional PUT, relying on server enforcement; S3 conditional uploads are limited to 1 GiB and use conditional multipart completion above 16 MiB. The app attempts to abort its own multipart upload ID on interruption without deleting the destination; abort or initiation can be unconfirmed and leave an unfinished upload, successful abort may still leave in-flight parts, and a lost completion response can mean the object exists. Known upload IDs are stored in a private journal and retried on a later connection to the same endpoint and account, with file locks protecting uploads still in progress; recovery relies on the provider's upload-ID uniqueness. Recovery requires a trusted configuration directory and working OS file locks; Windows journal files inherit the directory's access controls. A crash before an upload ID is recorded cannot be recovered this way. Configure an S3 lifecycle rule for abandoned multipart uploads. An unchanged ETag does not necessarily mean the object has not changed. FTP/FTPS uploads require explicit confirmation of the rename race and a server supporting STOU and the RFC 1123 FILE response. They upload to a server-generated temporary file and rename it to the requested destination; a competing destination can be overwritten despite the pre-rename check, and interruption or failure may leave a temporary file requiring manual cleanup. Existing destinations require separate overwrite approval. Other queued overwrites are rejected until they can be made safe. Other configurations require further verification.

LinSCP is one native Tauri desktop application. There is no browser build and
no HTTP server: the page only ever talks to the shell's in-process IPC. The
retired console client, PowerShell module and .NET CLI wrapper are not shipped.

## Build

Install Rust 1.89+, Node.js 22+, npm, `dpkg-dev`, `pkg-config`,
`libwebkit2gtk-4.1-dev`, `libgtk-3-dev`, `libayatana-appindicator3-dev`, and
`librsvg2-dev`. Build from the repository root:

```sh
dpkg-buildpackage -b -us -uc
```

The resulting package installs `linscp-gui`, one desktop entry and icons.
`linscp-gui` also carries the optional, per-user file-manager
integration: `linscp-gui --install-shell-integration` adds an "Upload with LinSCP"
entry to Dolphin, GNOME Files and Nemo, which stages the selection and returns,
and `linscp-gui --uninstall-shell-integration` removes exactly what it wrote. The
window then offers the staged selection for confirmation; nothing is transferred
without it. The frontend is embedded in the executable, but WebKitGTK and other
shared libraries are runtime dependencies. Launch LinSCP from the desktop menu
or run `linscp-gui` in a graphical session; settings live in the normal user
configuration directory.

For an uninstalled build and test commands, see the [main README](../readme.md).
