# Synchronization and editing evidence

Synchronization rejects unsafe names returned by remote listings and granted-folder providers before building paths, as well as non-UTF-8 local names. On Windows it also rejects reserved device names, several aliasing or invalid characters, and case-colliding paths; colon-bearing names are refused on all platforms. The case check is conservative and is not a complete model of all Windows filesystem aliases. The keep-up-to-date watcher retains events received while its initial synchronization is running, instead of discarding them before the next wait. A deterministic host test injects a change during that first pass and requires another pass before the long polling interval.

Remote editor, external-editor staging and content search downloads enforce their byte limits while streaming, even if server metadata understates a file's size. Search rejects unsafe remote and granted-provider listing names. Local searches read from files with a per-file bound; failed and oversized reads are charged to the search budget. Granted-folder searches still read entire documents through the provider bridge, which has a separate, larger document limit. The browser can retry an undecodable file using an explicitly selected encoding without replacing the currently open editor; backend encoding names are matched case-insensitively. Invalid sequences and unrepresentable output remain errors, and binary detection is heuristic.

Linux and Windows mock-session regressions for the watcher, bounded reads, listing validation and partial remote-delete reporting passed in [CI run 46115208371](https://github.com/unsubstantiation/LinSCP/actions/runs/46115208371). The browser retry and lowercase-encoding tests pass in the jsdom UI suite on Linux. Follow-up CI at [run 46115520925](https://github.com/unsubstantiation/LinSCP/actions/runs/46115520925) covers the subsequent validation-order adjustment.

The Linux service test `live_webdav_sync_encoding_and_interrupted_delete` ran against an isolated loopback WebDAV server in [CI run 46118176504](https://github.com/unsubstantiation/LinSCP/actions/runs/46118176504): a nested one-way upload, Windows-1252 and BOM-bearing UTF-16LE read/search/save, binary and unrepresentable-output refusal, and a TCP connection deliberately dropped on the second child deletion. The response reported the partial failure and the test inspected the surviving tree. This is one controlled server and does not prove behavior of other implementations. A [packaged Android emulator run](https://github.com/unsubstantiation/LinSCP/actions/runs/46117216549) also exercised Windows-1252 remote editing/search and the interrupted deletion through WebView IPC against that fixture; it did not exercise the retry dialog itself.

Recursive remote deletion is not transactional: a connection failure may leave a partially deleted tree. The editor's remote save checks second-resolution modification times, not an atomic compare-and-swap, so concurrent changes can still be overwritten. Watcher behavior on other providers and physical devices, and broader live-server encoding compatibility remain unverified.

The Linux and Windows host regressions, including the Windows case-alias refusal, oversized-search budgets and malicious provider listings, passed in [CI run 46118431298](https://github.com/unsubstantiation/LinSCP/actions/runs/46118431298). That run also passed the engine mock-SFTP suite and the service suite excluding live cases. The Android run used commit `11ed4b0`, before the final local/provider search budget changes; those final changes have host tests but have not been rerun on Android.
