# Windows storage inventory for the unified application file

This is an inventory of the current native Rust application, not an implementation of the proposed storage change. Paths below are relative to the active configuration root unless otherwise stated. On Windows that root is normally `%APPDATA%\LinSCP`; `LINSCP_CONFIG_DIR` overrides it ([platform paths](../crates/linscp-platform/src/lib.rs), [Windows default](../crates/linscp-platform/src/windows.rs)). This inventory focuses on Windows; Android's Keystore and app-private paths and Linux's paths must not be inadvertently changed by a Windows-specific switch.

The requested end state is one persistent application data file beside the executable, with permissions applied to the file rather than the executable's parent directory. Existing installations need not be migrated. This is a proposed classification, not a claim that the new file or behavior exists today. A user-selected export or a transfer destination is not application configuration and must not be redirected into that file.

## Persistent application data

| Current path | Contents and current treatment | Main code and integration notes |
| --- | --- | --- |
| `sessions.key` | Password-wrapped random master key; the Windows password vault is application-managed. Legacy formats are recognized for migration. | [password vault](../crates/linscp-platform/src/password_vault.rs), [legacy loader](../crates/linscp-platform/src/lib.rs). A single-file format must carry its own password/KDF and authentication information; do not store an unwrapped key on disk. |
| `sessions.ini` | Saved sites and secret fields; the service password vault encrypts the full session store. | [session store](../crates/linscp-engine/src/session_store.rs); [service](../crates/linscp-service/src/lib.rs); [script](../crates/linscp-engine/src/script.rs). | `s3_multipart_resume.json` | S3 multipart upload checkpoints for resumption; stored separately by the protocol layer. | [connection construction](../crates/linscp-engine/src/url_and_raw.rs), [S3 resume store](../crates/linscp-proto/src/s3.rs). | `s3-conditional-cleanup/upload-*.json` | Durable records of outstanding conditional S3 multipart uploads; entries include endpoint, bucket, object key and upload ID, not credentials. Per-record OS locks distinguish live uploads from abandoned work. Consolidation must preserve crash recovery and concurrent ownership, not simply delete the journal. |

The full backup covers a subset of this table and has its own password-encrypted portable format, not the live vault format. It collects and rewraps vault keys and validates references; restore uses a configuration lock, a quiescence check and a durable undo journal ([backup engine](../crates/linscp-engine/src/backup.rs), [restore journal](../crates/linscp-engine/src/restore_journal.rs), [service handlers](../crates/linscp-service/src/backup.rs)). Moving live data into one file must retain these semantics and define explicitly whether sync and S3 state belong in backups.

## Runtime, recovery, and external files

These are not ordinary long-term settings, but some deliberately survive crashes or must be accessible before unlock. A single persistent data file does not by itself eliminate them.

| Path or location | Role and implications |
| --- | --- |
| `.configuration.lock` | OS-backed exclusive configuration lock ([platform](../crates/linscp-platform/src/lib.rs)). A lock on a file that is atomically replaced can lose its cross-process identity; keep a stable locking mechanism. |
| `.instance-ipc` | Local single-instance activation endpoint and authentication token, used before unlock ([platform](../crates/linscp-platform/src/lib.rs)). It cannot simply become an encrypted record requiring an unlocked vault. |
| `.full-restore-journal` | Encrypted undo journal for interrupted full restore ([restore journal](../crates/linscp-engine/src/restore_journal.rs)). A new single-file transaction may change the recovery scheme, but must remain durable and fail closed. |
| `shell-manifests/` and `.claim.lock` | Short-lived shell-upload manifests and interprocess claim lock ([operations](../crates/linscp-service/src/ops.rs)). Explorer can launch another process; retain safe handoff and single-consumer behavior. |
| `tmp/unlocked-keys/<pid>/` | Temporary materialized SSH/TLS keys for consumers that need paths; cleanup on lock/startup and on guard drop ([service key helpers](../crates/linscp-service/src/lib.rs), [vault handlers](../crates/linscp-service/src/vault.rs)). These may contain plaintext. Moving persistent keys alone does not eliminate them. |
| `edit-tmp/`, `external-edit/`, `drop-staging/` | Staged editor buffers and drag-and-drop content; may contain user file plaintext ([operations](../crates/linscp-service/src/ops.rs), [service](../crates/linscp-service/src/lib.rs)). They are runtime working files, potentially left after abnormal termination. |
| System temporary directory and transfer destinations | Cross-server/SAF staging, editor scratch, and destination-side `.filepart`/temporary files support transfers and resume ([queue](../crates/linscp-service/src/queue.rs), [transfer](../crates/linscp-engine/src/transfer.rs), [editor](../crates/linscp-engine/src/editor.rs)). They contain user data and have their own cleanup and atomic-publication requirements. |
| `session-actions.xml` or configured log path | Optional action log, potentially in the config root or a user-selected location ([service](../crates/linscp-service/src/lib.rs), [logging](../crates/linscp-engine/src/xml_log.rs)). Log files are output, not automatically a vault record; their policy needs a decision. |
| User-selected backup/export/import files, external SSH keys and certificates | External files remain at paths chosen by the user. Full backups and key/session exports are separate artifacts; imports must not silently delete the source. Vault-managed keys are distinct from external paths. |
| Windows integrations and external services | Explorer/URL registration, OS shell, SSH agent and external editors are integrations, not vault stores. Consolidating LinSCP-owned persistent data does not remove those integrations or manage third-party credentials. |

## Constraints for the next chunks

1. **File permissions:** `write_private_file_atomic` calls `ensure_private_dir`, which on Windows applies an owner-only DACL to the parent. Do not use it with the executable directory. The existing `write_owner_only_file_atomic` avoids changing the parent, but its Windows temporary-file creation currently uses ordinary `OpenOptions`; the existing permission test only checks Unix mode bits. It is not sufficient evidence of an owner-only Windows file DACL or safe creation in a shared directory ([platform writer](../crates/linscp-platform/src/lib.rs), [Windows implementation](../crates/linscp-platform/src/windows.rs)). Implement and test secure creation/replacement on Windows, including inherited ACLs and reparse points, before relying on it.
2. **Locked startup:** preferences, instance activation and configuration locking currently happen before vault unlock. Define how setup, locked startup and CLI/Explorer flows work without exposing confidential data or treating an inaccessible vault as empty.
3. **Concurrency and durability:** multiple processes, background transfers, restore and sync update different stores today. A single container needs coordinated read/modify/write transactions, stable locking, atomic replacement, crash recovery, and errors propagated to callers.
4. **Read-only installation:** executable directories such as `Program Files` may not be writable. Fail with an actionable error; do not silently create a second vault elsewhere. Establish how the explicit `LINSCP_CONFIG_DIR` override should interact with the new location.
5. **Coverage:** exercise fresh setup, restart, wrong password, corruption, import/export, lock/unlock, concurrent writers, interrupted replacement, per-file Windows DACL and unchanged parent permissions. Include script and shell handoff paths, S3 recovery and sync baselines, not only GUI site saves.
6. **Do not drop compatibility accidentally:** tests and APIs expose file paths and cleanup categories; backup, key/session interchange and scripts directly access several stores. Update those consumers deliberately. No old-file migration is required, but current supported import formats still need to work.
